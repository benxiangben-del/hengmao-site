# 后台、Supabase 与新版前台连接说明

## 当前结论

旧后台必须先改造后才能连接新版前台。旧后台是一条产品对应一组中文字段的结构，不能可靠表达新版前台需要的双语发布、型号级安装/使用/安全指南、媒体权属、资料下载和首页推荐位。

现在代码已统一到 `content_v2` 内容模型：

- 后台编辑 `content_v2` 产品记录；
- 新版前台读取同一记录，只显示当前语言已发布的内容；
- 没有配置 Supabase 时，前后台进入明确的本地演示/结构预览模式；
- 草稿、未审核参数、未批准素材和未发布翻译不会作为正式公开内容读取。

## 为什么目前还不能称为“正式上线”

仓库中没有 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`，也无法从本地代码判断线上 Supabase 是否已经完成备份、是否允许新增 `content_v2` schema、是否已建立管理员账号。因此当前完成的是连接代码、后台界面与安全迁移方案，不是对线上数据库的未授权修改。

后台打开后显示“未连接数据库”是正确状态。此时保存只写入当前浏览器的 `localStorage`，不会写入服务器，也不会影响客户看到的网站。

## 正式连接顺序

1. 在 Supabase 控制台为现有项目创建备份或确认可回滚点。
2. 审核并执行 `docs/supabase-content-model-v2.sql`，创建隔离的 `content_v2` 表结构。
3. 在 Supabase 的 API 设置中，将 `content_v2` 加入 Exposed schemas。
4. 审核并执行 `docs/supabase-content-v2-production-access.sql`，建立公开读取、后台角色和 Storage 权限。
5. 创建后台管理员用户，并在该用户的 `app_metadata` 中设置：

   ```json
   { "content_role": "admin" }
   ```

6. 在本机创建不提交到 Git 的 `.env.local`：

   ```dotenv
   VITE_SUPABASE_URL=https://你的项目.supabase.co
   VITE_SUPABASE_ANON_KEY=你的公开 anon key
   ```

   前端只能使用 anon key。`service_role` 密钥不得放入网页代码或 `.env.local`。

7. 重启开发服务器。后台应由“结构预览模式”变为登录页，登录后显示“Supabase 已连接”。
8. 先新建一款草稿产品，验证中英文、参数、指南和首页推荐；不要直接迁移全部旧数据。
9. 通过审核门槛后发布该产品，分别检查中文和英文产品中心、详情页、型号搜索与首页轮播。
10. 小范围验收通过后，再规划旧表数据迁移和正式部署。

## 上线验收标准

- 未登录用户不能读取草稿和后台记录；
- 已登录但没有 `content_role` 的账号不能修改内容；
- 中文未发布时不显示中文，英文未发布时不使用中文代替；
- 产品必须同时具备已发布双语内容、审核参数、批准主图和审核安全指南，后台才允许设为正式发布；
- 首页轮播只引用正式发布产品；
- 删除或归档产品不会破坏历史资料，Storage 文件删除须单独确认；
- `.env.local` 和所有密钥均未进入 Git。

## 回滚原则

`content_v2` 与旧 `public.products` / `public.product_images` 隔离。在新版数据通过验收前，旧表不删除、不覆盖。若连接失败，可移除本地环境变量恢复演示模式；若数据库迁移失败，使用 Supabase 备份回滚，而不是手工删除生产数据。
