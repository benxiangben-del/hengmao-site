# 上海恒猫机电官网开发规范

版本：0.1  
日期：2026-07-17  
状态：已确认的项目基线

## 1. 总体原则

- 小步迁移，不一次性推倒重写。
- 先建立可验证结构，再迁移现有内容。
- 所有外部可见信息以真实资料为依据。
- 每个阶段保持主站可构建、可预览、可回滚。
- 桌面仓库 `C:\Users\XR\Desktop\hengmao-site` 是唯一正式工作仓库。
- `_archive/` 只用于恢复，不参与构建、搜索或提交。

## 2. 建议目录边界

```text
src/
├── app/                  # 应用入口、路由、providers
├── pages/                # 页面组合
├── ui/                   # 无业务基础组件
├── components/           # 通用复合组件
├── features/
│   ├── products/
│   ├── support/
│   ├── company/
│   └── admin/
├── lib/                  # Supabase、SEO、日志与工具
├── content/              # 默认内容、词库与迁移数据
└── styles/               # tokens、globals、组件样式

tests/
├── unit/
├── integration/
└── e2e/
```

实施过程中允许旧文件与新结构并存，迁移完成后再删除旧代码。

## 3. 技术决策规则

- 保留 React + Vite 作为起点。
- 引入路由、预渲染、测试或格式工具前，检查官方文档、维护状态和与当前 Node/React 版本的兼容性。
- 不为一个小效果增加大型依赖。
- 依赖必须记录用途；未使用依赖及时移除。
- 锁文件必须随依赖变更提交。
- 不在没有迁移收益证明时更换整个技术栈。

## 4. 代码规范

- 组件单一职责，页面负责组合，不直接承载所有数据访问逻辑。
- 数据获取集中在服务层或 feature 层。
- UI 组件不直接访问 Supabase。
- 业务字段使用稳定英文标识；显示文案来自语言内容。
- 避免巨型对象和重复的中英文默认数据散落在多个文件。
- 错误信息分为用户信息与诊断信息，前台不暴露数据库细节。
- 删除操作必须二次确认，并显示影响对象。

## 5. 类型与校验

首期可选择渐进式 TypeScript 或运行时 schema 校验，但必须达到：

- Supabase 返回数据在进入组件前校验/标准化。
- 产品、翻译、参数、媒体和指南有明确类型契约。
- 表单输入在客户端和数据库约束层均校验。
- URL、文件类型、大小、状态和 locale 使用允许列表。

是否全面迁移 TypeScript 在骨架阶段用一个模块试点后决定，不一次性改写全部文件。

## 6. 样式规范

- 所有通用视觉值来自 `04-design-system.md` 对应令牌。
- 禁止在页面组件中持续增加无来源颜色和间距。
- 移动端从内容需要出发，不以缩小桌面版作为方案。
- 组件样式与组件同边界管理，避免新的单体超长 CSS 文件。
- 支持 `prefers-reduced-motion`、键盘焦点和高对比可读性。

## 7. 双语规范

- UI 文案使用稳定 key，不在 JSX 中重复硬编码中英文。
- 产品内容由数据库翻译记录提供。
- 型号、参数值和媒体为共享事实，标签与描述按 locale 区分。
- 语言切换保留当前路由和内容。
- 缺少正式翻译时明确回退策略，不能把未审核机器翻译当作正式内容。

## 8. 数据库与迁移

- 数据库变更使用有序 migration 文件，不直接只在 Dashboard 手工修改。
- migration 必须可重复执行或明确前置状态。
- 生产迁移前备份表和 Storage 对象清单。
- 不直接删除旧字段或旧表，先完成双读/迁移验证。
- RLS 策略与表结构一同审查和测试。
- 所有写操作验证当前角色和允许状态。

## 9. 安全

- `.env` 不提交；仅提交无秘密的 `.env.example`。
- 浏览器只使用 Supabase anon key。
- Service role、数据库密码和私钥不得进入前端、仓库、日志或截图。
- 后台账号启用强密码；条件允许时增加 MFA。
- 上传限制 MIME、扩展名、大小和目标目录。
- 富文本或外部 URL 输出前验证，防止脚本注入与危险协议。
- 联系表单使用速率限制、反垃圾和服务端校验。
- 用户错误页面不泄露表名、策略和环境变量状态。

## 10. 测试层级

### 单元测试

- 型号规范化与搜索
- URL/slug 生成
- 语言回退
- 参数和媒体标准化

### 组件测试

- ProductCard
- SearchBox
- SpecificationTable
- InstructionSteps
- SafetyNotice
- LanguageSwitcher

### 集成测试

- 产品列表和详情读取
- 中英文对应内容
- 后台登录、编辑、上传和发布
- RLS 允许与拒绝路径

### 端到端测试

- 已知型号搜索到产品页
- 产品页打开安装视频与下载资料
- 语言切换停留在对应产品
- 移动端导航
- 404 和无结果恢复路径

## 11. 质量门槛

每个实施批次至少执行：

1. 依赖安装完整性检查
2. lint/格式检查（工具引入后）
3. 自动化测试（对应范围）
4. `npm run build`
5. 桌面与移动关键页面视觉检查
6. Git diff 审查

发布前增加：SEO、无障碍、性能、链接、表单、安全和真实内容检查。

## 12. Git 与变更管理

- 一个实施阶段对应一个清晰变更集。
- 提交信息描述结果，不使用“update/fix stuff”。
- 不提交 `node_modules`、`dist`、日志、压缩包、`.env` 与 `_archive`。
- 不覆盖用户未提交的无关修改。
- 结构迁移与大规模视觉修改分开提交，便于回滚和定位问题。
- 数据库 migration 与依赖它的代码在同一阶段交付。

## 13. 环境与发布

建议环境：

- Local：本地开发
- Preview：每个阶段的可分享预览
- Production：正式域名

预览与生产使用不同的 Supabase 项目或至少不同数据边界。预览环境禁止搜索引擎索引。

发布流程：

`本地验证 → 预览部署 → 内容/视觉/移动端验收 → 数据迁移 → 生产部署 → 冒烟测试 → 监控`

## 14. 文档维护

以下变更必须同步更新文档：

- 导航、页面与路由
- 设计令牌与核心组件
- 数据表、字段与 RLS
- 环境变量
- 部署流程
- 内容录入与发布流程

文档与代码冲突时，不应默默忽略；先确认哪一方是正确目标并同步修正。

## 15. 验收标准

- 每次变更范围清晰且可回滚。
- 生产构建始终可验证。
- UI、数据访问和业务逻辑边界明确。
- 双语、移动端、安全和 SEO 不是上线末期补丁。
- 数据库变更可追踪并经过权限测试。
- 不把秘密、归档和生成文件提交到 Git。
